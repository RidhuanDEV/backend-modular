# Provider migration and upgrade

Never modify released migration IDs/content. PostgreSQL and MySQL have independent histories selected for native migrate/status/rollback by provider config. Core 2026_10_03_000001 fixture represents Laravel pre-hardening schema (refresh token family_id/hash/expiry/consumed_at and legacy notifications without sequence). Hardening 000002 backfills families preserving maximum legacy expiry and ended-family consumption, rejecting mixed-user families. Notifications sort by created_at then UUID deterministically per recipient, counters become max allocated sequence, old PENDING without job becomes FAILED. Then FK/unique/non-null constraints are added. This is a native Laravel fixture, not Express/Go/.NET data import.

DDL atomicity differs: MySQL schema changes may implicitly commit. Back up and use reviewed migration release jobs; rollback command is a tool, not proof of atomic recovery. APP_KEY/JWT rotation and provider changes require separate operational design. Existing .env/data/storage histories survive installs and redeployment.

Cleanup preserves consumed refresh traces until authoritative family ended beyond retention30d; old terminal jobs may delete, pending/leased jobs and persisted notifications remain. Audit off by default; opt-in365d recommended. Orphan files older24h require owned UUID object name and final metadata recheck; this is not a distributed SQL/filesystem transaction.

## Refresh token transport

By default the refresh token travels in the JSON body. Set `REFRESH_TOKEN_TRANSPORT=cookie` to keep it in an httpOnly cookie instead (path `/api/auth`, 30-day max age): login and refresh then return only `token`, and refresh/logout read the cookie when the body has no `refreshToken`. Cookie-authenticated refresh/logout requests must send an `X-Requested-With` header (any value); this custom header forces a CORS preflight, so only allowlisted origins can use the cookie, and requests without it get 403. CORS then allows credentials for the exact `CORS_ORIGINS` list, so browsers must call with `credentials: "include"`. `REFRESH_COOKIE_SAMESITE` defaults to `lax`, which works when the frontend shares the site (for example `app.example.com` and `api.example.com`; set `REFRESH_COOKIE_DOMAIN=.example.com` to share one cookie). A frontend on a different site needs `REFRESH_COOKIE_SAMESITE=none` (which requires `REFRESH_COOKIE_SECURE=true`); browsers that block third-party cookies (Safari by default) will still drop it, so keep body mode for fully cross-site clients. `REFRESH_COOKIE_SECURE` defaults to true; set it to false only for plain-HTTP local development.

## Least-privilege PostgreSQL role (Compose)

The bundled PostgreSQL container creates `POSTGRES_USER` as a superuser, and by default the application connects as that user. For deployments built from this Compose file, set `APP_DB_USER` and `APP_DB_PASSWORD` before the first start of an empty volume: `scripts/postgres-init-app-role.sh` then creates a login role without superuser, `CREATEDB` or `CREATEROLE` that can only read and write rows (`SELECT/INSERT/UPDATE/DELETE` on tables, sequence usage) in schema `public`, including tables created by later migrations. Point the application connection at that role and give the migration service the owner credentials through `MIGRATION_DB_USERNAME`/`MIGRATION_DB_PASSWORD`. Defaults are unchanged when these variables are empty. For an existing volume run `docker compose exec postgres bash /docker-entrypoint-initdb.d/10-app-role.sh` once. MySQL Compose already connects as the non-root `MYSQL_USER`.
